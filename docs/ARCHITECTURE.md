# v0.12.0 analytics architecture

Operational records remain the source for current account/content/interaction counts. Audience analytics is additive and starts with an explicit trackingSince timestamp. Public totals are cached per period for 30 seconds; authenticated ranking discovery is queried separately so block/mute filtering cannot bleed between viewers. Database-side distinct counts avoid transferring member-ID lists for aggregate activity metrics. Private statistics are guarded by analytics.view; analytics.manage controls public-ranking configuration. The administrator migration adds these permissions only to the reserved role.

Audience storage: AnalyticsVisitorDay keys (Nigeria date,daily HMAC browser digest); AnalyticsHit stores a daily hashed browser/event nonce for page deduplication; AnalyticsMember holds first/last observation and total observed days; AnalyticsMemberDay keys (account,Nigeria date). AnalyticsDay, AnalyticsPageDay and AnalyticsSourceDay hold numeric aggregates. Browser UUIDs rotate daily in localStorage and are never authentication credentials. Account identity comes from the current server session. Pulses require a visible, recently used page and do not count as page views. Page signals follow pathname navigation, not private URL/query/hash contents. Browser-source categories are estimates; fraud-resistant ad attribution is a different future system.

A transaction uses INSERT ON CONFLICT skipDuplicates for browser/day, member/day and page-event keys and atomic increments for rollups. Same-browser tabs, retries and React Strict Mode do not multiply daily browser counts or an identical page nonce. Different devices can still count separately. DNT/GPC and browser opt-out stop audience collection; operational counts remain non-identifying. No audience endpoint returns hashes, per-person histories, IPs or full paths/referrers. Authentication/account activity summaries remain until account deletion; raw retention is enforced by the API's housekeeping timer, with aggregate rows retained.

The API observes response status/duration into a tiny per-day process buffer, flushed about every minute. Health and collection endpoints are excluded. Flush failures retain the buffer for retry; a crash can lose unflushed observations. Current RSS/heap/uptime belong to this API process and are not cluster resources or an uptime percentage. PostgreSQL database size may be unavailable where privileges/functions are restricted. Image bytes are current Media records under the existing local quota, not CDN bandwidth or cloud billing.

The same 60-second housekeeping service captures closed Monday–Sunday weeks, catches up at most four per tick and prunes old hash/member-day rows. A unique weekStart plus conflict-safe insert prevents duplicate snapshots between instances. Existing snapshots are never recalculated; publicData and adminData are separate JSON aggregates. Public endpoints explicitly select only publicData. Inventory/status counts describe capture-time eligibility; period metrics use the week's date bounds. No historical visitor data or reports are seeded by the migration. A stopped API cannot capture/prune until restart. Historical active-member deduplication unavailable beyond raw retention is not invented.

Finance, commerce/ticketing, paid-campaign conversion, independent uptime/mail-delivery and provider bandwidth reporting use explicit availability panels until their source systems exist. Week-two cohort reporting switches from waiting_for_data when mature eligible registrations exist; it is not based on assumed historical visits. CSV exports contain approved aggregates and scope timestamps, not arbitrary profile/post text or private identities. Public rankings are off by default and can be enabled later without implementing a second ranking engine; users can exclude their account/posts from that public discovery feature.

# v0.11.0 text entities

PostToken stores original label, UTF-16 start/end, kind and either canonical hashtag or an account foreign key. A composite post/start primary key preserves distinct occurrences, indexes support hashtag/post and account lookups, and post deletion cascades. Account deletion sets the target null so original text remains readable. Read projections resolve the current username from the persisted account ID; an old username being reassigned cannot redirect an already stored mention.

Server parsing ignores recognised HTTP(S)/www URL and email ranges and checks token boundaries. Distinct-token and occurrence limits are checked before writing. The normal post-creation transaction resolves mention targets through active-account/bilateral-block rules and creates nested entity rows. Post INSERT reply/quote triggers run before nested entity INSERT triggers, allowing deterministic priority and one mention notification per recipient. The shared notification helper suppresses self activity and recipient mutes/blocks. Public/recipient read visibility is checked again at query time. No media, private profile fields or post body snapshot is duplicated into the entity/notification records.

A separate committed enum migration precedes use of MENTION, matching PostgreSQL enum transaction requirements. The schema does not parse historical content or attach past usernames to present-day accounts. Article discussion posts generated by editorial publication are not entity-indexed; rich article mentions are a future separate editor integration.

The composer debounces suggestions for 250 ms, aborts stale requests and uses an accessible listbox with keyboard/pointer selection. Suggestions appear above the textarea so they do not obstruct send controls or change their position on blur. Exact tag feeds select visible Post records rather than FeedEvent records, including matching replies and avoiding duplicated reposts. Discovery lists alphabetical matching visible tags and makes no claim of trending popularity. Native PostgreSQL query plans/load and shared-host limits still need deployment testing.

# v0.10.0 publishing architecture

Article remains the public snapshot. ArticleWorkingCopy is a separate private JSON payload with author, optimistic version, last published version, UTC schedule timestamp, scheduling actor and failure message. Draft creation does not create a public Article or FeedEvent. Existing stories are read into a version-0 working copy only when opened, and persisted only when saved. No old article is migrated into a new public URL.

A conditional UPDATE with the expected version acquires the working-copy row lock inside a transaction. Concurrent saves or workers cannot claim the same revision. Article/discussion updates and schedule clearing commit together; rollback leaves the revision eligible for a later attempt. Permission/account checks are performed during publication, not only when the schedule is created. On an actionable publication failure the schedule is cleared with an error and the draft is retained for review. Failure to query the database leaves due records in place for a later tick. Publication/cancellation/unpublication are audited; typing does not generate an audit row per autosave.

PublishingService uses an unref'd 15-second timer, bounded to 20 due articles per scan, with an in-process overlap guard. The database conditional claim also prevents duplicate publication between app instances; it does not rely on a Redis lock or in-memory job record. A stopped API cannot execute schedules. Due records are checked after restart. PUBLISHING_WORKER_DISABLED=true disables automatic scanning, intended for isolated tests; do not set this on the only production worker. Native multi-connection PostgreSQL contention and hosting process lifetime still require deployment verification.

The React studio serializes in-flight saves and debounces typing for 1.5 seconds. Its Saved marker corresponds to the acknowledged payload, not merely the last request finishing. Changes made during an in-flight save remain dirty and are saved next. The page warns before browser unload with unsaved changes and blocks link clicks while dirty. It does not promise offline retention or interception of every browser navigation. Errors have manual retry/close controls; conflicts require reopening. The native modal preview loads the saved server copy and uses the same HTML sanitizer/rendering rules as the public article. Scheduled copies disable inputs and the rich editor until cancellation.

# v0.9.1 delivery architecture

Sync polling has a 60-request/minute allowance per session plus a 1,800-request/minute IP backstop. Other routes retain their previous limits. This avoids grouping all regular polling into the old 180/minute allowance for one campus Wi-Fi IP; it does not establish a tested hosting capacity.

LIKE enum creation is a separate committed migration before the trigger migration, satisfying PostgreSQL's enum transaction rules. Like events reference the existing post and recipient; no uploaded media or text snapshot is copied.

One account-scoped provider owns live sync and title state. Sync cursors detect arrivals independently from unread-total increases, avoiding false alerts from simple count changes. Foreground arrivals create a toast and refresh the inbox. Background arrivals may display an opted-in generic browser notification. Counts/title reset on session changes, old in-flight results are ignored, and outstanding alerts close on cleanup. The first sync establishes a baseline and does not toast historic activity.

Browser preferences are the only new localStorage data (explicit per-account opt-in; no credentials or inbox contents). The notification-only service worker has install/activate/click handlers, no fetch caching and a fixed same-origin inbox destination. OS permissions are requested only from an explicit Enable button. Registration/showNotification is preferred; a Notification constructor fallback is used without service-worker support. This is not a push subscription system: no VAPID keys, Push API subscriptions, push queue or closed-browser delivery are claimed. Five/fifteen-second polling is best-effort and subject to browser throttling and existing API rate/resource limits; native host load testing remains pending.

# v0.9 notification architecture

Notification references a recipient User, actor User and optional source/context Post. Timestamp columns use TIMESTAMPTZ(3), and every Prisma pool connection requests UTC through startup options. This avoids pg adapter offset normalization changing read boundaries; existing connection options are preserved before the final timezone setting. Indexed recipient/date/id supports cursor pagination; recipient/readAt supports unread queries. Event keys uniquely identify source activity. Database triggers append notifications in the source transaction; a failure rolls both back. Undo triggers remove follow/repost entries. Existing social content is not scanned or backfilled during the upgrade.

notificationVisibility is shared by list, unread count and read mutations. It combines session ownership, bidirectional blocks, recipient mutes, actor status and source/context postVisibility. A suppressed event cannot leak through the unread counter or by submitting its ID to the read endpoint. Post previews are generated from currently visible content, never stored copies of hidden text. Article status and original conversation-owner blocks remain part of visibility. Reads return only bounded public actor fields and internal destinations.

A single React provider owns count polling for both navigation surfaces. It keys displayed counts to the current account, cancels stale sessions, ignores old in-flight results after explicit count updates, pauses periodic polls in hidden tabs and backs off on errors. Inbox requests have cancellation/generation guards for filters and pagination. Notification state is stored on the server; no credentials or notification list are written to browser localStorage. Refresh is explicit for list contents; there is no live-delivery promise. This keeps the initial deployment compatible with the existing Node/PostgreSQL service arrangement.

# v0.8 safety architecture

Block and Mute use composite primary keys and indexed target IDs. A shared visibleAuthor/postVisibility predicate applies active-account, publication, article/community and viewer safety rules across feed events, post queries, reply/quote counts and media/article reads. Feed events filter both the original author and repost actor. A nullable conversation-owner User relation carries the root-author block boundary through nested replies; the migration backfills legacy trees. New article discussion posts also set this owner.

Follow creation and block/follow removal use serializable transactions with bounded retries, so concurrent requests cannot leave a new follow after a committed block. Native PostgreSQL concurrency/load verification remains pending. Members manage only their own lists. Reports remain available to permission-checked moderators, with a separate audit record for each review/moderation action. Personal filters do not prevent privileged evidence review. Historical engagement totals are aggregate data and are not rewritten by blocks. Public posts remain public outside an authenticated viewer's personalized experience. This is a beta implementation, not a guarantee that another account cannot view public content.

# v0.6 additions

Post can reference another Post as a quote and a cached LinkPreview. Public projections re-query quoted sources through the standard visibility predicate and intentionally stop after one level. FeedEvent represents root publication or repost by an actor. PostgreSQL triggers create/delete events consistently for API, editorial publication and future database imports; the migration backfills existing posts/reposts. New migrations therefore require permission to create PL/pgSQL functions and triggers.

LinkPreviewService fetches public metadata through a bounded DNS-pinned HTTP client, never a browser or embedded script. Page/thumbnail requests are validated independently. Thumbnails are stored in PostgreSQL for the initial bounded cache; this is separate from user Media storage and is not yet backed by R2/CDN. Outbound preview requests depend on the deployment allowing public DNS and HTTP/HTTPS; the client intentionally does not inherit proxy environment variables or browser cookies. Unsafe/failing previews never prevent post creation.

# Architecture — checkpoint 0.3

One modular NestJS API and one separate React application. PostgreSQL stores accounts, role assignments, menus, sessions, interests, communities, posts, social relations, member-day views, articles, reports, action tokens and audits. Prisma migrations preserve the original v0.1/v0.2 migration and add 202610160001_community_features. No destructive reset is part of upgrade.

## Authorization

Sessions contain random bearer credentials stored only as SHA-256 hashes in the database. Browser credentials use host-only HttpOnly/SameSite=Lax cookies, Secure in production, with exact-origin checks for unsafe cookie requests. Explicit bearer clients remain supported. Each request reloads account status and role permissions; role changes apply without waiting for a JWT to expire. Suspension revokes sessions. Bookmarks require authentication; public profiles select explicit safe fields.

Permissions: moderation.manage, users.manage, roles.manage, menus.manage, articles.write, articles.publish, communities.manage and topics.manage. Administrators receive all; moderators moderate; editors write/publish; ordinary members use public participation flows. Roles can combine permissions. Public registration cannot set permissions. The Administrator role definition is protected. Removing the final active role-management account is rejected by role assignment/account suspension checks. Custom role changes also preserve a role-management holder. Serializable transactions protect assignment/suspension from concurrent changes; a conflicting transaction may need retry.

Flat menus have a label, validated destination, order, enabled flag, optional required permission and members-only flag. The API filters navigation, but API authorization is independent. Public content can still be accessed directly if a navigation menu is hidden. Group membership governs posting in public communities; it is not proof of department affiliation. All groups in this version are public.

## Content and feeds

Short posts and replies remain distinct from long-form Article records. Articles have DRAFT/PUBLISHED status and publication dates. Editors may manage their own drafts; publishing requires articles.publish. Public article reads exclude drafts and suspended authors. Legacy IDs/source keys are nullable unique pairs for future importer mapping. Plain text and safe outbound links are rendered without HTML execution.

Latest is chronological. Following includes followed authors and their repost eligibility. Reposts reference originals; there is no duplicated body or independent repost chronology yet. For you filters to chosen topics or joined communities, falling back to the global feed when no interests/memberships exist. It is a deterministic initial filter, not a trained recommendation algorithm. Following retrieval caps at 5,000 followed account IDs pending a larger-scale SQL strategy.

Likes, reposts and bookmarks use unique account/post keys; PUT is idempotent, DELETE removes the relation. Views are unique per account/post/UTC day and publicly aggregated only. Bookmarks are not a public engagement count. Link detection never fetches remote URLs, avoiding a new URL-fetch/SSRF surface.

## Account recovery and moderation

Action tokens are purpose-bound, hashed, expiring and consumed atomically. Resets revoke all sessions. Local file delivery is development-only; production refuses file transport and requires SMTP. No real provider was contacted during development. Generic forgot-password responses do not disclose matching accounts. Resend is rate limited and per-account cooled down.

New reports snapshot the reported body, remain private to moderators and do not auto-hide posts. Staff hide/restore posts, resolve reports and suspend/reactivate accounts. Actions record actor, target, reason and time in AuditLog. The current retention, legal-request, evidence-export and appeals policies still need review; an audit table alone does not meet every investigation requirement.

## Operations

No required Redis, worker daemon or WebSocket service. SMTP sends synchronously with finite timeouts; production volume may justify an outbox/worker. A small PostgreSQL pool defaults to 3. API limits are per process (default 180/minute; tighter auth limits). This is not distributed anti-abuse protection. Exact proxy/IP behavior must be verified on the host. Build artifacts and secrets remain separate; privileged bootstrap uses trusted local database access.
